# ADR-0001: Миттєве SMS-підтвердження замість фонових SMS за таймером

- **Статус:** прийнято
- **Дата:** 23.10.2026
- **Пов'язано:** REQ-09, UC10, NFR-04, NFR-09, `spec.md` (розділ «Поза обсягом»)

## Контекст

Початкова версія REQ-09 передбачала SMS-нагадування за 24 години до прийому. Це фоновий процес за часом, а не дія актора. Для нього потрібні планувальник задач і черга повторних спроб, яких немає в обраному стеку (REST API + PostgreSQL, NFR-09).

## Decision Drivers

- **D1. Відповідність Use Case без фонових таймерів.** UC10 «Надіслати SMS-підтвердження запису» розширює UC1 і запускається дією актора (створенням прийому, REQ-09), а не часом.
- **D2. Стек REST API + PostgreSQL без воркерів (NFR-09).** Система не має планувальника задач, черги та фонових процесів, тому SMS має надсилатися в межах HTTP-запиту.
- **D3. Ліміт відгуку до 800 мс (NFR-04).** Створення прийому належить до складних операцій, тож додаткові виклики не повинні виводити час відповіді для 95% запитів за 800 мс.

## Considered Options

### Варіант 1. Миттєве SMS при записі

Booking Service після збереження прийому викликає SMS Gateway в межах того самого запиту, якщо пацієнт указав номер або обрав SMS-підтвердження (UC10 `extend` UC1).

- (+) D1: SMS є прямим наслідком дії пацієнта («прийом створено»), без часових тригерів; вписується в UC1 і UC10.
- (+) D2: не потрібні планувальник, воркер і черга; достатньо виклику з Booking Service.
- (+) Пацієнт одразу бачить результат (статус доставки `SENT`); збій SMS не скасовує прийом.
- (−) D3: виклик SMS Gateway додає затримку до запиту на запис, тому потрібен короткий таймаут, щоб вкластися в 800 мс.
- (−) Нагадування перед візитом немає, тому ризик неявок вищий.
- (−) Без воркера немає автоматичних повторних спроб: якщо SMS не доставлено, повторне надсилання не виконується.

### Варіант 2. Фонові нагадування за таймером

Планувальник задач за 24 години до прийому ставить SMS у чергу, а воркер надсилає її через SMS Gateway.

- (+) Зменшує ризик неявок: пацієнт отримує нагадування перед візитом.
- (+) D3: виклик SMS Gateway виконується поза запитом на запис, тому не впливає на його час відгуку; можливі повторні спроби.
- (−) D2: потрібні планувальник, воркер і черга задач, тобто додаткова інфраструктура поверх REST API + PostgreSQL.
- (−) D1: тригером є час, а не дія актора, тому для процесу потрібен окремий use case із системним тригером.
- (−) Складніше супроводжувати: треба не надсилати нагадування за скасованими й перенесеними прийомами.

### Варіант 3. Повна відмова від SMS

SMS Gateway не використовується; пацієнт бачить підтвердження лише у Web App.

- (+) D1, D2, D3: найпростіше рішення, без додаткових дій, процесів і викликів, що впливали б на час відгуку.
- (+) Немає залежності від зовнішнього сервісу SMS Gateway.
- (−) REQ-09 і UC10 залишаються без реалізації; SMS Gateway зникає з акторів і sequence diagram.
- (−) Пацієнт не отримує підтвердження поза інтерфейсом, а нагадування немає взагалі.

## Рішення

Обрано **варіант 1** — миттєве SMS при записі. Фонові SMS за таймером не реалізуються. Booking Service одразу після збереження прийому викликає SMS Gateway і надсилає підтвердження запису, якщо пацієнт указав номер телефону або обрав SMS-підтвердження (блок `opt` у sequence diagram).

## Наслідки

- (+) Не потрібен фоновий планувальник: SMS надсилається лише в межах запиту на запис, поведінка детермінована.
- (+) REQ-09 повністю покривається зв'язкою UC1 і UC10 (`extend`).
- (+) Збій SMS не скасовує прийом: Web App показує повідомлення про SMS лише зі статусом доставки `SENT`.
- (−) Нагадування перед візитом немає, тому ризик неявок вищий.
- (−) Виклик SMS Gateway виконується всередині запиту на запис, тому має короткий таймаут, щоб вкластися в NFR-04 (до 800 мс).
