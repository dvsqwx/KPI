# ADR-0004: Шарова компонентна архітектура: окремі сервіси бекенду та шар Data Access перед PostgreSQL

- **Status:** прийнято
- **Date:** 03.11.2026
- **Related:** UC1, UC3, UC4, UC5, UC7, UC9, UC10, UC12, REQ-01, REQ-02, REQ-09, REQ-12, NFR-02, NFR-03, NFR-04, NFR-05, NFR-06, NFR-09, `spec.md` (розділ 12), `component-diagram.mmd`, `er-diagram.mmd`, `sequence-diagram.mmd`

## Context (Контекст)

Система «A-Dent» охоплює три групи use cases: запис і розклад прийомів (UC1, UC3, UC4), довідники (UC12) та рахунки й оплати (UC5, UC7, UC9). Усі вони працюють із вісьмома сутностями моделі даних у PostgreSQL. Запис на прийом є найскладнішою операцією: `findAvailableRoom`, `findConflictingAppointments`, `saveAppointment` і `saveAppointmentServices` виконуються в одній транзакції (`BEGIN`…`COMMIT` / `ROLLBACK`), а після неї за потреби викликається зовнішній SMS Gateway. Стек зафіксовано в NFR-09: REST API з JSON і PostgreSQL, без воркерів і черг. Потрібно вирішити, як розділити бекенд на компоненти та чи звертатися до бази даних безпосередньо із сервісів, чи через окремий шар.

## Decision Drivers (Рушійні чинники)

- **D1. Відповідність доменам і use cases.** Запис, довідники та рахунки мають різні сутності, правила й причини змін (REQ-01, REQ-02, REQ-12, REQ-05–REQ-07); зміна в одному домені не повинна зачіпати інші.
- **D2. Єдина точка перевірок безпеки й навантаження.** JWT (NFR-05, NFR-06) і ліміт 150 RPS з відповіддю `429` (NFR-02, NFR-03) мають перевірятися один раз на вході, до будь-якої бізнес-логіки.
- **D3. Узгодженість даних і відсутність дублювання запитів.** Транзакція запису не повинна допускати подвійного бронювання (REQ-02), а однакові запити до `SERVICE` і `ROOM` потрібні і запису, і довідникам.
- **D4. Стек і ліміт відгуку (NFR-04, NFR-09).** Рішення не повинно вимагати додаткової інфраструктури (брокерів, воркерів) і має вкладатися в 300 мс для читання та 800 мс для складних операцій.

## Considered Options (Розглянуті варіанти)

### Варіант 1. Три сервіси та шар Data Access (шарова архітектура)
Рівні: Web App → REST API Controller → Booking Service, Catalog Service, Billing Service → Data Access (репозиторії та `TransactionManager`) → PostgreSQL. SMS Gateway розташований поза межею системи й викликається лише з Booking Service. Сервіси не викликають один одного, а до бази звертаються тільки через інтерфейси репозиторіїв.
- `(+) D1:` кожен сервіс відповідає за свою групу use cases: Booking (UC1, UC3, UC4), Catalog (UC12), Billing (UC5, UC7, UC9); зміни правил оплати не зачіпають логіку запису.
- `(+) D2:` REST API Controller перевіряє JWT (`validateJwt`) і ліміт запитів один раз на вході, тому сервіси отримують лише перевірені запити.
- `(+) D3:` усі запити з sequence-діаграм (`findAvailableSlots`, `findAvailableRoom`, `findConflictingAppointments`, `saveAppointment` та інші) зосереджені в репозиторіях; транзакцією керує `TransactionManager` через `ITransaction`; `ServiceRepository` і `RoomRepository` спільні для Booking і Catalog, тому запити не дублюються.
- `(+) D4:` усе це один backend-застосунок і одна база PostgreSQL без черг і воркерів; виклики між компонентами відбуваються через інтерфейси в межах процесу.
- `(−)` Компонентів і інтерфейсів більше, ніж у простіших варіантах, і прості операції проходять кілька шарів (контролер, сервіс, репозиторій).
- `(−) D4:` кожен додатковий шар додає час до відповіді, тому NFR-04 потрібно перевіряти вимірюванням на профілі навантаження.
- `(−)` Спільні репозиторії зв'язують Booking і Catalog: зміна сигнатури `IServiceRepository` чи `IRoomRepository` зачіпає обидва сервіси.

### Варіант 2. Один монолітний сервіс із репозиторіями
Єдиний `Clinic Service` реалізує всі use cases; репозиторії та `TransactionManager` залишаються.
- `(+) D4:` найменше компонентів і найпростіші розгортання та налагодження.
- `(+) D3:` шар Data Access зберігається, тому запити та транзакції так само зосереджені в одному місці.
- `(−) D1:` логіка запису, довідників і рахунків змішується в одному модулі; зміна правил оплати (REQ-05–REQ-07, REQ-10) торкається того самого коду, що й UC1.
- `(−)` Немає меж між use cases, тому складніше тестувати запис і оплату окремо, а сервіс з часом перетворюється на великий неподільний модуль.
- `(−)` Залежності між функціями не видно на діаграмі, бо всі вони всередині одного компонента.

### Варіант 3. Три сервіси, що звертаються до PostgreSQL напряму (без Data Access)
Booking, Catalog і Billing самі формують SQL-запити та керують транзакціями.
- `(+) D4:` на один шар менше, тому шлях до бази найкоротший.
- `(+) D1:` розподіл на три сервіси зберігається.
- `(−) D3:` SQL-запити та керування транзакціями розкидані по трьох сервісах; однакові запити до `SERVICE` і `ROOM` дублюються в Booking і Catalog.
- `(−) D3:` коректність транзакції запису залежить від того, що сервіс правильно відкриває й закриває її; помилка збільшує ризик подвійного бронювання (REQ-02).
- `(−)` Бізнес-логіка жорстко прив'язана до PostgreSQL (NFR-09): сервіси важко тестувати без реальної бази, а зміна моделі (наприклад, додавання `actual_price`) зачіпає кілька сервісів.

## Decision (Рішення)

Обрано **Варіант 1**. Бекенд розділено на три сервіси за доменами, бо запис, довідники та рахунки мають різні сутності й причини змін (D1): `Booking Service` працює з прийомами, `Catalog Service` — з довідниками, `Billing Service` — з рахунками. Сервіси не викликають один одного й залежать лише від репозиторіїв. Перед PostgreSQL виділено шар Data Access, бо він збирає всі запити в одному місці, надає спільні `IServiceRepository` та `IRoomRepository` обом сервісам і керує транзакцією через `ITransaction` (D3). Вхідні перевірки (JWT, ліміт запитів) виконує `REST API Controller` до виклику сервісів (D2). SMS Gateway лишається поза межею системи й викликається лише з Booking Service (UC10).

## Consequences (Наслідки)

- Залежності йдуть лише вниз: Web App → REST API Controller → сервіси → Data Access → PostgreSQL; між сервісами залежностей немає. Це показано в `component-diagram.mmd` з усіма п'ятьма рівнями та межею системи.
- Сервіси є окремими компонентами одного backend-застосунку: один процес і одна база PostgreSQL. Якщо надалі знадобиться винести сервіс в окремий процес, його залежності вже виражені інтерфейсами, але таке рішення потребуватиме окремого ADR.
- Методи з sequence-діаграм стають операціями репозиторіїв; межі транзакції `BEGIN`, `COMMIT` і `ROLLBACK` задає Booking Service через `ITransaction`.
- Sequence- та activity-діаграми показують бекенд спрощено, як одного учасника «Booking Service» без `REST API Controller` і Data Access. За розділом 12 `spec.md` перевірка JWT (`validateJwt`) належить `REST API Controller`.
- Для кожного додаткового шару потрібно перевірити NFR-04 (300 мс для читання, 800 мс для складних операцій) вимірюванням, а не припущенням.
- Нові операції інтерфейсів, яких немає в попередніх діаграмах (`getSchedule`, `cancelAppointment`, `getPatientAppointments`, `manageSpecialties`, `manageRooms`, `manageServices`, `createInvoice`, `registerPayment`, `registerRefund`), потрібно узгодити зі `spec.md` під час реалізації.
