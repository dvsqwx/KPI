# Специфікація концептуальної моделі — «Приватна стоматологічна клініка A-Dent »

## 1. Сутності та їх бізнес-призначення

| Сутність | Бізнес-призначення |
|---|---|
| **Пацієнт** (Patient) | Особа, яка звертається до клініки за стоматологічними послугами; є ініціатором запису на прийом. |
| **Лікар** (Doctor) | Медичний працівник клініки, який проводить прийоми та надає послуги в межах своєї спеціальності. |
| **Спеціальність** (Specialty) | Довідник напрямів стоматології (терапевт, хірург, ортодонт, гігієніст тощо), за яким класифікуються лікарі. |
| **Кабінет** (Room) | Фізичне приміщення клініки, обладнане для прийому пацієнтів; ресурс, що бронюється на час прийому. |
| **Послуга** (Service) | Довідник медичних маніпуляцій клініки (огляд, лікування карієсу, чистка, видалення тощо) з фіксованою ціною. |
| **Прийом** (Appointment) | Факт (подія) візиту пацієнта до конкретного лікаря в конкретному кабінеті в конкретний час; центральна сутність процесу. |
| **Рахунок** (Invoice) | Фінансовий документ, що виставляється за результатами прийому та фіксує суму й статус оплати наданих послуг. |

## 2. Атрибути сутностей

**Пацієнт**
- patient_id — uuid, PK
- full_name — string, обов'язково
- birth_date — date
- phone — string, обов'язково
- email — string
- address — string
- registration_date — datetime

**Лікар**
- doctor_id — uuid, PK
- full_name — string, обов'язково
- phone — string
- email — string
- hire_date — date
- license_number — string (номер сертифіката/ліцензії)

**Спеціальність**
- specialty_id — uuid, PK
- name — string, обов'язково
- description — string

**Кабінет**
- room_id — uuid, PK
- number — string, обов'язково (номер/назва кабінету)
- floor — int
- equipment_description — string

**Послуга**
- service_id — uuid, PK
- name — string, обов'язково
- description — string
- price — decimal, обов'язково
- duration_minutes — int
- category — string

**Прийом**
- appointment_id — uuid, PK
- patient_id — uuid, FK → Пацієнт, обов'язково
- doctor_id — uuid, FK → Лікар, обов'язково
- room_id — uuid, FK → Кабінет, обов'язково
- date_time — datetime, обов'язково
- duration_minutes — int, обов'язково
- status — string (enum: заплановано / завершено / скасовано / пацієнт не з'явився)
- notes — string

**Рахунок**
- invoice_id — uuid, PK
- appointment_id — uuid, FK → Прийом, обов'язково, унікальне
- issue_date — datetime, обов'язково
- total_amount — decimal, обов'язково
- paid_amount — decimal, обов'язково
- payment_status — string (enum: не оплачено / оплачено частково / оплачено повністю)
- payment_method — string
- paid_date — datetime, опційно (null до моменту сплати)

## 3. Зв'язки

| Зв'язок | Тип | Кардинальність та обов'язковість |
|---|---|---|
| Лікар — Спеціальність | M : M | Один лікар може мати 1..* спеціальностей; одна спеціальність може бути у 0..* лікарів. |
| Пацієнт — Прийом | 1 : M | Один пацієнт має 0..* прийомів; кожен прийом обов'язково належить рівно 1 пацієнту. |
| Лікар — Прийом | 1 : M | Один лікар проводить 0..* прийомів; кожен прийом обов'язково проводить рівно 1 лікар. |
| Кабінет — Прийом | 1 : M | Один кабінет використовується для 0..* прийомів; кожен прийом обов'язково відбувається рівно в 1 кабінеті. |
| Прийом — Послуга | M : M | Один прийом включає 1..* послуг (обов'язково хоча б одну); одна послуга може входити до 0..* прийомів. Реалізує факт «які послуги надані під час візиту». |
| Прийом — Рахунок | 1 : 1 (опційний з боку прийому) | Один прийом має 0..1 рахунок (рахунок ще може бути не сформований); кожен рахунок обов'язково відповідає рівно 1 прийому. |

Зв'язки з довідниками Кабінет і Послуга через прийом — обов'язкові з боку залежної сутності (Прийом) і необов'язкові (0..*) з боку довідника, оскільки довідникова позиція може ще не мати пов'язаних записів. Зв'язок Лікар–Спеціальність є винятком: він реалізований як M:M, тому обов'язковість асиметрична — лікар обов'язково має 1..* спеціальностей, а спеціальність може мати 0..* лікарів (довідникова позиція може існувати без жодного призначеного лікаря).

## 4. Критерії прийняття моделі

Модель вважається прийнятою, якщо виконані такі критерії:

- **Відповідність 3NF (третій нормальній формі).** Кожен неключовий атрибут кожної сутності залежить виключно від первинного ключа цієї сутності, повністю (без часткової залежності від складеного ключа) і безпосередньо (без транзитивної залежності через інший неключовий атрибут). Атрибути, що описують окрему предметну одиницю (спеціальність лікаря, ціна й тривалість послуги, статус і сума рахунка), винесені у власні сутності/поля, а не дублюються в залежних сутностях.
- **Референційна цілісність.** Кожне значення зовнішнього ключа (FK) обов'язково відповідає існуючому значенню первинного ключа (PK) пов'язаної сутності: patient_id/doctor_id/room_id у «Прийомі», appointment_id у «Рахунку». Для M:M-зв'язку Лікар–Спеціальність кожна пара (лікар, спеціальність) обов'язково посилається на існуючі записи обох сутностей; на логічному/фізичному рівні цей зв'язок реалізується через асоціативну сутність із двома FK (doctor_id, specialty_id). Видалення чи зміна запису-«батька» не повинні залишати «осиротілих» посилань у залежних сутностях; обов'язковість/необов'язковість зв'язку (0..1, 1, 0..*, 1..*) відповідає розділу 3.
- **Типізація ключів.** Усі первинні (PK) та зовнішні (FK) ключі мають єдиний концептуальний тип **uuid**, незалежний від фізичної СУБД; жоден ключ не використовує тип int чи інший фізичний числовий тип. Типи неключових атрибутів обмежені узгодженим переліком концептуальних типів: string, int, decimal, date, datetime, boolean.
- **Відсутність дублювання.** Кожен факт предметної області зберігається рівно в одному місці: довідникові дані (спеціальності, кабінети, послуги) не копіюються в сутність «Прийом», а лише посилаються через FK; атрибути пацієнта/лікаря не повторюються в «Рахунку»; зв'язок «Прийом–Послуга» реалізований через M:M, а не через повторювані атрибути послуг усередині «Прийому».

## 5. Актори та їхні цілі

| Актор | Тип | Головні цілі |
|---|---|---|
| **Пацієнт** | Первинний, людина | Записатися на прийом; переглянути/скасувати власні записи; оплатити рахунок; переглянути історію лікування. |
| **Лікар** | Первинний, людина | Переглянути власний розклад прийомів; провести прийом і зафіксувати надані послуги та статус візиту. |
| **Адміністратор** | Первинний, людина | Керувати довідниками (спеціальності, кабінети, послуги); керувати розкладом прийомів (запис/скасування від імені пацієнта); контролювати оплати та ініціювати повернення коштів. |
| **Платіжна система** (зовнішній сервіс) | Вторинний, зовнішня система | Обробити платіж пацієнта за рахунком і повернути клініці статус транзакції (успіх/відмова), включно з поверненнями коштів. |

## 6. Вимоги у форматі EARS

| ID | Вимога |
|---|---|
| REQ-01 | WHEN пацієнт обирає лікаря, послугу, дату та вільний часовий слот, система SHALL створити прийом зі статусом «заплановано». |
| REQ-02 | IF обраний часовий слот кабінету або лікаря вже зайнятий іншим прийомом, THEN система SHALL відхилити запис і повідомити пацієнта про конфлікт. |
| REQ-03 | WHILE прийом має статус «заплановано», система SHALL показувати його активним у розкладі лікаря. |
| REQ-04 | WHEN лікар позначає прийом як «завершено» із переліком наданих послуг, система SHALL розрахувати total_amount рахунка як суму цін обраних послуг. |
| REQ-05 | WHEN пацієнт ініціює оплату рахунка, система SHALL передати платіжній системі суму до сплати та ідентифікатор рахунка. |
| REQ-06 | WHEN платіжна система повертає статус «успішно», система SHALL оновити payment_status рахунка та зафіксувати paid_amount і paid_date. |
| REQ-07 | IF платіжна система повертає статус «відмова», THEN система SHALL залишити payment_status без змін і повідомити пацієнта про помилку оплати. |
| REQ-08 | WHEN пацієнт скасовує прийом зі статусом «заплановано» щонайменше за 24 години до дати прийому, система SHALL змінити статус прийому на «скасовано» і звільнити кабінет та час лікаря. |
| REQ-09 | WHERE для прийому активоване нагадування, система SHALL надіслати пацієнту нагадування за 24 години до запланованого часу прийому. |
| REQ-10 | WHEN адміністратор скасовує вже оплачений прийом, система SHALL ініціювати повернення коштів через платіжну систему. |
| REQ-11 | Система SHALL гарантувати, що кожен лікар має призначену щонайменше одну спеціальність. |
| REQ-12 | Система SHALL дозволяти адміністратору додавати, редагувати та деактивувати записи довідників (спеціальності, кабінети, послуги). |
| REQ-13 | WHEN лікар або адміністратор відкриває розклад на обрану дату, система SHALL відобразити всі прийоми цього лікаря чи кабінету за цей день. |
| REQ-14 | IF прийом не має пов'язаного рахунка протягом 24 годин після завершення, THEN система SHALL позначити прийом як такий, що потребує уваги адміністратора. |
| REQ-15 | WHEN пацієнт відкриває розділ «Мої прийоми», система SHALL відобразити список усіх його прийомів у хронологічному порядку. |
| REQ-16 | WHEN пацієнт відкриває історію лікування, система SHALL відобразити перелік завершених прийомів із наданими послугами по кожному. |
| REQ-17 | Система SHALL вимагати автентифікацію лікаря та адміністратора перед наданням доступу до функцій системи. |

## 7. User stories та Gherkin-сценарії

**US-01 (Пацієнт).** Як пацієнт, я хочу записатися на прийом до лікаря обраної спеціальності на зручний час, щоб отримати стоматологічну послугу.

```gherkin
Функція: Запис пацієнта на прийом

  Сценарій: Успішний запис на вільний час
    Припустимо пацієнт обрав лікаря зі спеціальністю "Терапевт"
    І пацієнт обрав послугу "Професійна чистка"
    Якщо пацієнт обирає вільний часовий слот 15.10.2026 10:00 у кабінеті №3
    То система створює прийом зі статусом "заплановано"
    І пацієнт отримує підтвердження запису

  Сценарій: Спроба записатися на зайнятий час
    Припустимо кабінет №3 вже заброньовано на 15.10.2026 10:00
    Якщо пацієнт намагається обрати цей самий час і кабінет
    То система відхиляє запис
    І повідомляє пацієнту про конфлікт часу
```

**US-02 (Пацієнт).** Як пацієнт, я хочу оплатити рахунок за прийом онлайн, щоб не оплачувати готівкою в клініці.

```gherkin
Функція: Оплата рахунка

  Сценарій: Успішна оплата
    Припустимо пацієнт має неоплачений рахунок на суму 1200 грн
    Якщо пацієнт ініціює оплату через платіжну систему
    І платіжна система повертає статус "успішно"
    То система встановлює payment_status "оплачено повністю"
    І фіксує paid_date поточною датою

  Сценарій: Відмова платіжної системи
    Припустимо пацієнт ініціює оплату рахунка
    Якщо платіжна система повертає статус "відмова"
    То payment_status рахунка залишається без змін
    І пацієнт бачить повідомлення про помилку оплати
```

**US-03 (Лікар).** Як лікар, я хочу бачити розклад своїх прийомів на день, щоб підготуватися до візитів пацієнтів.

```gherkin
Функція: Перегляд розкладу лікаря

  Сценарій: Перегляд прийомів на обрану дату
    Припустимо лікар має 3 прийоми, заплановані на 15.10.2026
    Якщо лікар відкриває розклад на 15.10.2026
    То система відображає всі 3 прийоми з часом, пацієнтом і кабінетом
```

**US-04 (Адміністратор).** Як адміністратор, я хочу керувати довідником послуг (додавати/редагувати ціни), щоб підтримувати актуальний прайс клініки.

```gherkin
Функція: Керування довідником послуг

  Сценарій: Зміна ціни послуги
    Припустимо послуга "Лікування карієсу" має ціну 800 грн
    Якщо адміністратор змінює ціну на 950 грн і зберігає зміни
    То довідник послуг відображає нову ціну 950 грн
    І наступні прийоми з цією послугою використовують нову ціну
```

**US-05 (Адміністратор).** Як адміністратор, я хочу ініціювати повернення коштів за скасований оплачений прийом, щоб закрити фінансове зобов'язання перед пацієнтом.

```gherkin
Функція: Повернення коштів

  Сценарій: Повернення коштів за скасований оплачений прийом
    Припустимо прийом оплачено повністю і ще не відбувся
    Якщо адміністратор скасовує цей прийом
    То система ініціює повернення коштів через платіжну систему
    І статус прийому змінюється на "скасовано"
```
