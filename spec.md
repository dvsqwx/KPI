# Специфікація концептуальної моделі — «Приватна стоматологічна клініка A-Dent»

## 1. Сутності та їх бізнес-призначення

| Сутність | Бізнес-призначення |
|---|---|
| **Пацієнт** (Patient) | Особа, яка звертається до клініки за стоматологічними послугами; є ініціатором запису на прийом. |
| **Лікар** (Doctor) | Медичний працівник клініки, який проводить прийоми та надає послуги в межах своєї спеціальності. |
| **Спеціальність** (Specialty) | Довідник напрямів стоматології (терапевт, хірург, ортодонт, гігієніст тощо), за яким класифікуються лікарі. |
| **Кабінет** (Room) | Фізичне приміщення клініки, обладнане для прийому пацієнтів; ресурс, що бронюється на час прийому. |
| **Послуга** (Service) | Довідник медичних маніпуляцій клініки (огляд, лікування карієсу, чистка, видалення тощо) з фіксованою ціною. |
| **Прийом** (Appointment) | Факт (подія) візиту пацієнта до конкретного лікаря в конкретному кабінеті в конкретний час; центральна сутність процесу. |
| **Послуга прийому** (AppointmentService) | Асоціативна сутність між Прийомом і Послугою: фіксує, які послуги входять до прийому, та ціну кожної послуги на момент запису (actual_price). |
| **Рахунок** (Invoice) | Рахунок на оплату прийому: формується після візиту або під час запису (якщо вноситься передоплата) та зберігає загальну суму, внесені кошти й статус оплати. |

## 2. Атрибути сутностей

**Пацієнт**
- patient_id — uuid, PK
- full_name — string, обов'язково
- birth_date — date
- phone — string, обов'язково
- email — string
- address — string
- registration_date — datetime

**Лікар**
- doctor_id — uuid, PK
- full_name — string, обов'язково
- phone — string
- email — string
- hire_date — date
- license_number — string (номер сертифіката/ліцензії)

**Спеціальність**
- specialty_id — uuid, PK
- name — string, обов'язково
- description — string

**Кабінет**
- room_id — uuid, PK
- number — string, обов'язково (номер/назва кабінету)
- floor — int
- equipment_description — string

**Послуга**
- service_id — uuid, PK
- name — string, обов'язково
- description — string
- price — decimal, обов'язково
- duration_minutes — int
- category — string

**Прийом**
- appointment_id — uuid, PK
- patient_id — uuid, FK → Пацієнт, обов'язково
- doctor_id — uuid, FK → Лікар, обов'язково
- room_id — uuid, FK → Кабінет, обов'язково
- date_time — datetime, обов'язково
- duration_minutes — int, обов'язково
- status — string (enum: заплановано / завершено / скасовано / пацієнт не з'явився)
- notes — string

**Послуга прийому** (appointment_id + service_id)
- appointment_id — uuid, PK, FK → Прийом
- service_id — uuid, PK, FK → Послуга
- actual_price — decimal, обов'язково (ціна послуги, зафіксована на момент запису на прийом)

**Рахунок**
- invoice_id — uuid, PK
- appointment_id — uuid, FK → Прийом, обов'язково, унікальне
- issue_date — datetime, обов'язково
- total_amount — decimal, обов'язково
- paid_amount — decimal, обов'язково
- payment_status — string (enum: не оплачено / оплачено частково / оплачено повністю)
- payment_method — string
- paid_date — datetime, опційно (null до моменту сплати)

## 3. Зв'язки

| Зв'язок | Тип | Кардинальність та обов'язковість |
|---|---|---|
| Лікар — Спеціальність | M : M | Один лікар може мати 1..* спеціальностей; одна спеціальність може бути у 0..* лікарів. |
| Пацієнт — Прийом | 1 : M | Один пацієнт має 0..* прийомів; кожен прийом обов'язково належить рівно 1 пацієнту. |
| Лікар — Прийом | 1 : M | Один лікар проводить 0..* прийомів; кожен прийом обов'язково проводить рівно 1 лікар. |
| Кабінет — Прийом | 1 : M | Один кабінет використовується для 0..* прийомів; кожен прийом обов'язково відбувається рівно в 1 кабінеті. |
| Прийом — Послуга | M : M (через асоціативну сутність «Послуга прийому») | Один прийом включає 1..* послуг (обов'язково хоча б одну); одна послуга може входити до 0..* прийомів. Зв'язок розкладається на два 1:M: Прийом (1) — Послуга прийому (1..*) та Послуга (1) — Послуга прийому (0..*). Для кожної пари фіксується ціна actual_price на момент запису на прийом. |
| Прийом — Рахунок | 1 : 1 (опційний з боку прийому) | Один прийом має 0..1 рахунок (формується під час запису для передоплати або після завершення прийому); кожен рахунок обов'язково відповідає рівно 1 прийому. |

Зв'язки з довідниками Кабінет і Послуга через прийом — обов'язкові з боку залежної сутності (Прийом) і необов'язкові (0..*) з боку довідника, оскільки довідникова позиція може ще не мати пов'язаних записів. Зв'язок Лікар–Спеціальність є винятком: він реалізований як M:M, тому обов'язковість асиметрична — лікар обов'язково має 1..* спеціальностей, а спеціальність може мати 0..* лікарів (довідникова позиція може існувати без жодного призначеного лікаря). При цьому зв'язок Прийом–Послуга винесено в окрему асоціативну сутність «Послуга прийому» через наявність власного атрибута ціни (actual_price), тоді як зв'язок Лікар–Спеціальність додаткових бізнес-атрибутів не має.

## 4. Критерії прийняття моделі

Модель вважається прийнятою, якщо виконані такі критерії:

- **Відповідність 3NF (третій нормальній формі).** Кожен неключовий атрибут кожної сутності залежить виключно від первинного ключа цієї сутності, повністю (без часткової залежності від складеного ключа) і безпосередньо (без транзитивної залежності через інший неключовий атрибут). Атрибути, що описують окрему предметну одиницю (спеціальність лікаря, ціна й тривалість послуги, статус і сума рахунка), винесені у власні сутності/поля, а не дублюються в залежних сутностях.
- **Референційна цілісність.** Кожне значення зовнішнього ключа (FK) обов'язково відповідає існуючому значенню первинного ключа (PK) пов'язаної сутності: patient_id/doctor_id/room_id у «Прийомі», appointment_id/service_id у «Послузі прийому», appointment_id у «Рахунку». Для M:M-зв'язку Лікар–Спеціальність кожна пара (лікар, спеціальність) обов'язково посилається на існуючі записи обох сутностей; на логічному/фізичному рівні цей зв'язок реалізується через асоціативну сутність із двома FK (doctor_id, specialty_id). Видалення чи зміна запису-«батька» не повинні залишати «осиротілих» посилань у залежних сутностях; обов'язковість/необов'язковість зв'язку (0..1, 1, 0..*, 1..*) відповідає розділу 3.
- **Типізація ключів.** Усі первинні (PK) та зовнішні (FK) ключі мають єдиний концептуальний тип **uuid**, незалежний від фізичної СУБД; жоден ключ не використовує тип int чи інший фізичний числовий тип. Типи неключових атрибутів обмежені узгодженим переліком концептуальних типів: string, int, decimal, date, datetime, boolean.
- **Відсутність дублювання.** Кожен факт предметної області зберігається рівно в одному місці: довідникові дані (спеціальності, кабінети, послуги) не копіюються в сутність «Прийом», а лише посилаються через FK; атрибути пацієнта/лікаря не повторюються в «Рахунку»; зв'язок «Прийом–Послуга» реалізований через асоціативну сутність, а не через повторювані атрибути послуг усередині «Прийому». Підсумкові поля duration_minutes (у «Прийомі»), total_amount та payment_status (у «Рахунку») зберігаються як зафіксовані знімки стану (snapshot) на момент операції, оскільки тривалість і ціни в довіднику послуг можуть змінюватися з часом.

## 5. Актори та їхні цілі

| Актор | Тип | Головні цілі |
|---|---|---|
| **Пацієнт** | Первинний, людина | Записатися на прийом; переглянути/скасувати власні записи; оплатити рахунок; переглянути історію лікування. |
| **Лікар** | Первинний, людина | Переглянути власний розклад прийомів; провести прийом і зафіксувати надані послуги та статус візиту. |
| **Адміністратор** | Первинний, людина | Керувати довідниками (спеціальності, кабінети, послуги); керувати розкладом прийомів (запис/скасування від імені пацієнта); контролювати оплати та ініціювати повернення коштів. |
| **SMS Gateway** (зовнішній сервіс) | Вторинний, зовнішня система | Надіслати пацієнту SMS-підтвердження запису на прийом і повернути статус доставки. |

## 6. Вимоги у форматі EARS

| ID | Вимога |
|---|---|
| REQ-01 | WHEN автентифікований пацієнт обирає лікаря, одну або кілька послуг, дату та вільний часовий слот, система SHALL створити прийом зі статусом «заплановано» і зберегти для кожної обраної послуги її ціну (actual_price). |
| REQ-02 | IF обраний часовий слот лікаря чи кабінету вже зайнятий іншим прийомом, THEN система SHALL відхилити запис із відповіддю 409 Conflict, не створювати прийом, повідомити пацієнта про конфлікт і запропонувати обрати інший час зі збереженням обраних послуг. |
| REQ-03 | WHILE прийом має статус «заплановано», система SHALL показувати його активним у розкладі лікаря. |
| REQ-04 | WHEN лікар позначає прийом як «завершено» із переліком наданих послуг, система SHALL розрахувати total_amount рахунка як суму зафіксованих цін (actual_price) обраних послуг. |
| REQ-05 | WHEN пацієнт підтверджує оплату рахунка із зазначенням суми та способу оплати (payment_method), система SHALL зареєструвати платіж за цим рахунком. |
| REQ-06 | WHEN платіж за рахунком зареєстровано, система SHALL оновити payment_status рахунка та зафіксувати paid_amount і paid_date. |
| REQ-07 | IF сума платежу перевищує залишок до сплати або рахунок уже оплачений повністю, THEN система SHALL відхилити платіж, залишити payment_status без змін і повідомити пацієнта про помилку оплати. |
| REQ-08 | WHEN пацієнт скасовує прийом зі статусом «заплановано» щонайменше за 24 години до дати прийому, система SHALL змінити статус прийому на «скасовано» і звільнити кабінет та час лікаря.<br>IF пацієнт скасовує прийом менше ніж за 24 години до дати прийому, THEN система SHALL відхилити скасування і повідомити, що скасувати такий прийом може лише адміністратор. |
| REQ-09 | WHERE пацієнт указав номер телефону або обрав SMS-підтвердження, WHEN прийом створено, система SHALL надіслати SMS-підтвердження через SMS Gateway і показати пацієнту повідомлення про надсилання, якщо SMS Gateway повернув статус доставки «SENT». |
| REQ-10 | WHEN адміністратор скасовує прийом, за яким рахунок уже оплачено, система SHALL зареєструвати повернення коштів за цим рахунком і оновити paid_amount та payment_status. |
| REQ-11 | Система SHALL гарантувати, що кожен лікар має призначену щонайменше одну спеціальність. |
| REQ-12 | Система SHALL дозволяти адміністратору додавати, редагувати та деактивувати записи довідників (спеціальності та їх призначення лікарям, кабінети, послуги). |
| REQ-13 | WHEN лікар або адміністратор відкриває розклад на обрану дату, система SHALL відобразити всі прийоми цього лікаря чи кабінету за цей день. |
| REQ-14 | IF прийом не має пов'язаного рахунка протягом 24 годин після завершення, THEN система SHALL позначити прийом як такий, що потребує уваги адміністратора. |
| REQ-15 | WHEN пацієнт відкриває розділ «Мої прийоми», система SHALL відобразити список усіх його прийомів у хронологічному порядку. |
| REQ-16 | WHEN пацієнт відкриває історію лікування, система SHALL відобразити перелік завершених прийомів із наданими послугами по кожному. |
| REQ-18 | WHEN пацієнт додає до запису кілька послуг, система SHALL розрахувати duration_minutes прийому як суму duration_minutes обраних послуг і пропонувати лише слоти, що вміщують цю тривалість. |
| REQ-19 | IF в обраного лікаря на вибрану дату немає жодного вільного інтервалу, що вміщує сумарну тривалість прийому, THEN система SHALL повідомити пацієнта про відсутність вільних вікон, не створювати прийом і запропонувати обрати іншу дату. |
| REQ-20 | IF неавтентифікований користувач намагається підтвердити запис на прийом, THEN система SHALL відхилити запит із відповіддю 401 Unauthorized, не створювати прийом і запропонувати увійти в систему. |

Вимогу REQ-17 (автентифікація) перенесено до нефункціональних вимог (NFR-05); ідентифікатор REQ-17 не використовується.

### Нефункціональні вимоги (NFR)

| ID | Категорія | Вимога |
|---|---|---|
| NFR-01 | Пристрої та браузери | Інтерфейс SHALL коректно відображатися на екранах шириною від 360 px (смартфон) до 1920 px (монітор) без горизонтального прокручування в двох останніх стабільних версіях Chrome, Firefox, Edge і Safari. |
| NFR-02 | Навантаження | Система SHALL штатно обслуговувати навантаження від 50 RPS (звичайне) до 150 RPS (пікове) без порушення NFR-04. |
| NFR-03 | Обмеження запитів | IF інтенсивність запитів перевищує 150 RPS, THEN система SHALL відхиляти надлишкові запити з відповіддю 429 Too Many Requests і заголовком Retry-After. |
| NFR-04 | Час відгуку | Для бази з 50 000 пацієнтів і 200 000 прийомів система SHALL відповідати для 95% запитів: не довше ніж за 300 мс на прості запити читання (розклад на день, список прийомів пацієнта, довідники) і не довше ніж за 800 мс на складні операції (пошук вільних слотів, створення прийому, формування рахунка, реєстрація платежу). |
| NFR-05 | Безпека: автентифікація | Система SHALL вимагати автентифікацію користувача перед наданням доступу до персональних функцій системи; запити без чинного токена SHALL відхилятися з відповіддю 401 Unauthorized (колишній REQ-17). |
| NFR-06 | Безпека: JWT | Автентифікація SHALL виконуватися за допомогою JWT, що передається в заголовку Authorization: Bearer; термін дії токена — 60 хвилин, після спливу система SHALL вимагати повторного входу. |
| NFR-07 | Безпека: паролі | Паролі SHALL зберігатися лише у вигляді bcrypt-хеша з параметром cost не менше 12; мінімальна довжина пароля — 8 символів. |
| NFR-08 | Мова інтерфейсу | Інтерфейс SHALL бути українською мовою (локаль uk-UA): дати у форматі ДД.ММ.РРРР, час у 24-годинному форматі, грошові суми в гривнях (UAH) із двома знаками після коми. |
| NFR-09 | Технологічний стек | Серверна частина SHALL бути реалізована як REST API з обміном у форматі JSON, а дані SHALL зберігатися в PostgreSQL; ідентифікатори сутностей — uuid. |

## 7. Gherkin-сценарії: UC1 «Записатися на прийом»

```gherkin
Функція: Запис пацієнта на прийом (UC1)
  Як пацієнт клініки,
  я хочу записатися на прийом до обраного лікаря на одну або кілька послуг,
  щоб отримати стоматологічну допомогу у зручний для мене час.

  Сценарій: Успішний запис із кількома послугами
    Припустимо пацієнт "Іван Мельник" увійшов у систему
    І лікар "Коваленко О.І." зі спеціальністю "Терапевт" має вільний інтервал 30.10.2026 з 10:00 до 11:30
    І послуга "Огляд" триває 30 хв і коштує 400 грн
    І послуга "Професійна чистка" триває 60 хв і коштує 1200 грн
    І пацієнт додав до запису обидві послуги, а система показала сумарну тривалість 90 хв
    І система запропонувала слот 30.10.2026 о 10:00, що вміщує 90 хв
    Якщо пацієнт підтверджує запис на 30.10.2026 о 10:00
    То система створює прийом зі статусом "заплановано" та duration_minutes 90
    І зберігає для кожної послуги її ціну actual_price: 400 грн і 1200 грн
    І пацієнт бачить підтвердження запису

  Сценарій: Обраний слот уже зайнятий
    Припустимо пацієнт "Іван Мельник" увійшов у систему
```

## 9. Sequence diagram: запис пацієнта на прийом через онлайн-форму

**Прецедент (UC1 «Записатися на прийом»).** Автентифікований пацієнт в онлайн-формі обирає лікаря, додає одну або кілька послуг, після чого система розраховує тривалість прийому та пропонує доступні часові вікна відповідної довжини. Пацієнт обирає бажаний час і надсилає форму. Booking Service валідує дані, автоматично підбирає вільний кабінет (room_id), перевіряє відсутність конфліктів у розкладі та створює прийом зі статусом `scheduled` («заплановано»); за бажанням пацієнта надсилається SMS-підтвердження. Прецедент реалізує REQ-01, REQ-02 і (разом із UC10 «Надіслати SMS-підтвердження запису») REQ-09; діаграма знаходиться у файлі sequence-diagram.mmd.

**Учасники** (ланцюг взаємодії: Patient → Web App → Booking Service → Database; для SMS-підтвердження Booking Service додатково викликає SMS Gateway):

| Учасник | Роль | Сутності моделі |
|---|---|---|
| **Patient** | Користувач, що записується на прийом | Пацієнт |
| **Web App** | Клієнтська частина: вибір лікаря й послуг, калькуляція тривалості, відображення вільних слотів, показ підтвердження або помилки | — |
| **Booking Service** | Серверна бізнес-логіка: валідація даних, розрахунок тривалості, автоматичний підбір вільного кабінету (`findAvailableRoom`), перевірка конфліктів, збереження прийому і послуг, виклик SMS-шлюзу | Пацієнт, Лікар, Кабінет, Послуга, Прийом, Послуга прийому |
| **Database** | Зберігання даних розкладу та зв'язку Прийом–Послуга | Пацієнт, Лікар, Кабінет, Послуга, Прийом, Послуга прийому |
| **SMS Gateway** | Зовнішній сервіс надсилання SMS: приймає номер і текст від Booking Service та повертає статус доставки | — (використовує `phone` з даних пацієнта або номер, указаний у формі) |

**Кроки успішного запису:**

1. Пацієнт обирає лікаря (`doctor_id`).
2. Для кожної обраної послуги (гілка `loop`): пацієнт додає послугу, Web App викликає `getService(service_id)`, Booking Service читає з БД `price` і `duration_minutes`, Web App оновлює підсумок — список послуг, сумарну вартість і загальну тривалість (`total_duration`).
3. Пацієнт обирає дату візиту. Web App викликає `getAvailableSlots(doctor_id, date, total_duration)`. Booking Service через `findAvailableSlots` визначає вільні часові слоти лікаря в межах робочого графіка клініки на основі існуючих записів у сутності «Прийом» (Appointment).
4. Пацієнт обирає зручний слот (`date_time`) із запропонованих вільних вікон. Пацієнт не обирає кабінет вручну — це внутрішній ресурс клініки.
5. Пацієнт надсилає форму (за бажанням указує номер телефону або обирає SMS-підтвердження), Web App викликає `createAppointment(patient_id, doctor_id, date_time, service_ids[], sms_confirmation, phone)`.
6. Booking Service перевіряє існування пацієнта (`findPatientById`).
7. Booking Service повторно вичитує послуги з БД (`findServicesByIds`) для гарантії достовірності цін і повторно розраховує `duration_minutes`.
8. Booking Service автоматично підбирає вільний кабінет (`findAvailableRoom(date_time, duration_minutes)`) із сутності «Кабінет» (Room), який не зайнятий іншим прийомом на цей часовий інтервал, і отримує `room_id`.
9. Booking Service перевіряє відсутність конфліктів (`findConflictingAppointments` за лікарем, отриманим кабінетом і інтервалом) — список конфліктів порожній.
10. В одній транзакції Booking Service зберігає прийом зі статусом `scheduled` (`saveAppointment`) та фіксує зв'язки Прийом–Послуга у сутності «Послуга прийому», передаючи колекцію послуг з індивідуальною фіксованою ціною для кожної позиції (`saveAppointmentServices(appointment_id, items: [{service_id, actual_price}])`).
11. Опційно (блок `opt`, use case UC10), якщо вказано номер або обрано SMS: Booking Service викликає `sendSms(phone, message_text)` у SMS Gateway, який повертає статус доставки (`SENT`).
12. Booking Service повертає `201 Created` з `appointment_id` і `sms_status`, Web App показує підтвердження.
13. Якщо статус SMS — `SENT` (другий блок `opt`), Web App додатково показує повідомлення «SMS confirmation sent».

**Альтернативна гілка (`alt / else`): обраний час зайняли.** Якщо між відображенням вільних слотів і відправкою форми інший користувач забронював цей же час, на кроці 9 `findConflictingAppointments` знаходить накладання. Booking Service повертає `409 Conflict (SLOT_UNAVAILABLE)`, транзакція не виконується, а Web App пропонує пацієнту обрати інший час зі збереженням набору послуг.

## 10. Поза обсягом

У цю версію системи не входять:

- **Фонові SMS-нагадування за таймером** (наприклад, за 24 години до прийому). Замість них реалізовано миттєве SMS-підтвердження під час запису (REQ-09, UC10); обґрунтування наведено в [ADR-0001](docs/adr/0001-instant-sms-confirmation.md).
- **Інтеграція із зовнішньою платіжною системою** (онлайн-еквайринг, обробка карткових платежів). Оплата рахунка лише реєструється в системі (REQ-05–REQ-07), повернення коштів — також (REQ-10).
- **Детальні Gherkin-сценарії для UC2–UC12.** У цій версії специфікації детально описано лише UC1 «Записатися на прийом».
