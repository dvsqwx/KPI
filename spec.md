# Специфікація концептуальної моделі — «Приватна стоматологічна клініка»

## 1. Сутності та їх бізнес-призначення

| Сутність | Бізнес-призначення |
|---|---|
| **Пацієнт** (Patient) | Особа, яка звертається до клініки за стоматологічними послугами; є ініціатором запису на прийом. |
| **Лікар** (Doctor) | Медичний працівник клініки, який проводить прийоми та надає послуги в межах своєї спеціальності. |
| **Спеціальність** (Specialty) | Довідник напрямів стоматології (терапевт, хірург, ортодонт, гігієніст тощо), за яким класифікуються лікарі. |
| **Кабінет** (Room) | Фізичне приміщення клініки, обладнане для прийому пацієнтів; ресурс, що бронюється на час прийому. |
| **Послуга** (Service) | Довідник медичних маніпуляцій клініки (огляд, лікування карієсу, чистка, видалення тощо) з фіксованою ціною. |
| **Прийом** (Appointment) | Факт (подія) візиту пацієнта до конкретного лікаря в конкретному кабінеті в конкретний час; центральна сутність процесу. |
| **Рахунок** (Invoice) | Фінансовий документ, що виставляється за результатами прийому та фіксує суму й статус оплати наданих послуг. |

## 2. Атрибути сутностей

**Пацієнт**
- patient_id — int, PK
- full_name — string, обов'язково
- birth_date — date
- phone — string, обов'язково
- email — string
- address — string
- registration_date — datetime

**Лікар**
- doctor_id — int, PK
- full_name — string, обов'язково
- specialty_id — int, FK → Спеціальність
- phone — string
- email — string
- hire_date — date
- license_number — string (номер сертифіката/ліцензії)

**Спеціальність**
- specialty_id — int, PK
- name — string, обов'язково
- description — text

**Кабінет**
- room_id — int, PK
- number — string, обов'язково (номер/назва кабінету)
- floor — int
- equipment_description — text

**Послуга**
- service_id — int, PK
- name — string, обов'язково
- description — text
- price — decimal, обов'язково
- duration_minutes — int
- category — string

**Прийом**
- appointment_id — int, PK
- patient_id — int, FK → Пацієнт, обов'язково
- doctor_id — int, FK → Лікар, обов'язково
- room_id — int, FK → Кабінет, обов'язково
- date_time — datetime, обов'язково
- status — string (enum: заплановано / завершено / скасовано / пацієнт не з'явився)
- notes — text

**Рахунок**
- invoice_id — int, PK
- appointment_id — int, FK → Прийом, обов'язково, унікальне
- issue_date — datetime, обов'язково
- total_amount — decimal, обов'язково
- payment_status — string (enum: не оплачено / оплачено частково / оплачено повністю)
- payment_method — string
- paid_date — datetime

## 3. Зв'язки

| Зв'язок | Тип | Кардинальність та обов'язковість |
|---|---|---|
| Спеціальність — Лікар | 1 : M | Одна спеціальність об'єднує 0..* лікарів; кожен лікар має рівно 1 обов'язкову спеціальність. |
| Пацієнт — Прийом | 1 : M | Один пацієнт має 0..* прийомів; кожен прийом обов'язково належить рівно 1 пацієнту. |
| Лікар — Прийом | 1 : M | Один лікар проводить 0..* прийомів; кожен прийом обов'язково проводить рівно 1 лікар. |
| Кабінет — Прийом | 1 : M | Один кабінет використовується для 0..* прийомів; кожен прийом обов'язково відбувається рівно в 1 кабінеті. |
| Прийом — Послуга | M : M | Один прийом включає 1..* послуг (обов'язково хоча б одну); одна послуга може входити до 0..* прийомів. Реалізує факт «які послуги надані під час візиту». |
| Прийом — Рахунок | 1 : 1 (опційний з боку прийому) | Один прийом має 0..1 рахунок (рахунок ще може бути не сформований); кожен рахунок обов'язково відповідає рівно 1 прийому. |

Усі зв'язки з довідниками (Спеціальність, Кабінет, Послуга) — обов'язкові з боку залежної сутності (Лікар, Прийом) і необов'язкові (0..*) з боку довідника, оскільки довідникова позиція може ще не мати пов'язаних записів.
