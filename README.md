# Стоматологічна клініка «A-Dent» — концептуальна модель, вимоги та взаємодія

Навчальний проєкт: предметна область інформаційної системи приватної стоматологічної клініки. Репозиторій містить концептуальну ER-модель даних, вимоги до системи (EARS, user stories, Gherkin), use case діаграму, матрицю трасування та sequence diagram запису на прийом. Система автоматизує запис пацієнтів, планування завантаження лікарів і кабінетів з урахуванням тривалості візитів, облік наданих послуг та контроль оплати рахунків.

**Базовий процес:** запис на прийом (вибір лікаря й послуг, розрахунок тривалості, вибір вільного слота) → прийом (лікар фіксує надані послуги) → формування рахунка → оплата повністю або частинами через зовнішню платіжну систему.

## Бізнес-логіка за ролями

* **Пацієнт:** обирає лікаря та одну чи кілька послуг, після чого отримує вільні слоти під сумарну тривалість візиту й записується на прийом (кабінет призначається системою). За бажанням отримує SMS-підтвердження. Також переглядає й скасовує свої записи, оплачує рахунок, переглядає історію лікування.
* **Лікар:** має одну або кілька спеціальностей, бачить свій розклад, проводить прийоми без накладання візитів і фіксує щонайменше одну надану послугу за прийом.
* **Адміністратор:** веде довідники спеціальностей, кабінетів і послуг, керує розкладом (запис і скасування від імені пацієнта), відстежує статуси оплат (не оплачено / частково / повністю) та ініціює повернення коштів.
* **Платіжна система** (зовнішній сервіс): обробляє платежі й повертає статус транзакції.
* **SMS Gateway** (зовнішній сервіс): надсилає SMS-підтвердження запису та повертає статус доставки; присутній у sequence diagram.

## Модель даних

Сім сутностей: **Пацієнт, Лікар, Спеціальність, Кабінет, Послуга, Прийом, Рахунок**.

* Усі ключі (PK/FK) мають єдиний концептуальний тип `uuid`.
* Зв'язки M:M: Лікар–Спеціальність і Прийом–Послуга (для кожної послуги прийому фіксується її ціна `actual_price`).
* Зв'язки 1:M: Пацієнт, Лікар і Кабінет → Прийом. Прийом має не більше одного Рахунка (1:0..1).
* Критерії прийняття: 3NF, референційна цілісність, типізація ключів, відсутність дублювання.

## Вимоги та use cases

У `spec.md` описано: акторів та їхні цілі, 17 вимог у форматі EARS, 5 user stories з Gherkin-сценаріями та матрицю трасування «вимоги × use cases» (M:M). Вимога REQ-09 (нагадування за 24 години до прийому) у матриці лишається непокритою: для неї немає use case, а SMS Gateway в sequence diagram обслуговує лише підтвердження запису.

## Взаємодія (Sequence)

Розділ 9 `spec.md` і `sequence-diagram.mmd` описують запис на прийом через онлайн-форму. Учасники: Patient → Web App → Booking Service → Database, а також SMS Gateway.

* **Порядок вибору:** лікар → послуги (блок `loop`) → дата → вільний слот під `total_duration`.
* **Кабінет:** `room_id` визначає Booking Service (`findAssignedRoom`), клієнт його не вибирає.
* **Гілки:** `alt / else` — успішний запис (`201 Created`) або зайнятий слот (`409 Conflict`); `opt` — SMS-підтвердження, якщо вказано номер або обрано SMS.
* **Збереження послуг:** колекція `items: [{service_id, actual_price}]`.
